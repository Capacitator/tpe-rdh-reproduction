# Four-pixel TPE authentication v2 revised supporting materials

This directory accompanies `Four_Pixel_TPE_Authentication_Report_v2_Revised.docx`. It supplements the prior v2 directory; it does not replace it. No result or p-value was tuned or changed.

## Recreate the six input pixel arrays

The six run inputs under `authenticated_tpe_nist_v2/input/images_512/` are ignored by Git and were omitted from the earlier committed bundle. The exact input file bytes are not included here. Matching 512×512 RGB pixel arrays are committed at `authenticated_tpe_nist_v2/output/metrics/visual_gallery/{airplane,baboon,couple,girl,lena,peppers}_original.png`. The helper `authenticated_tpe_nist_v2/scripts/prepare_four_pixel_inputs.py` copies those references under the filenames expected by the runner and checks dimensions and RGB pixel hashes. Couple and Girl originated as 256×256 TIFFs in `tpe_rdh_reproduction/input/uct_colour/`; the experiment used their 512×512 gallery versions, not the raw 256×256 TIFFs. The other four tracked TIFFs are 512×512.

The metric CSV records hashes of the omitted PNG file bytes. Recreated files from the gallery may have different PNG byte hashes while preserving the exact RGB pixels; compare pixel hashes for input equivalence. A fresh encryption run uses new random keys and nonces, so ciphertext bytes, PSNR and bundle sizes can differ even with identical input pixels.

## Key handling and verification

Both the 32-byte TPE key and 32-byte authentication key are required to verify/decrypt a saved PNG+sidecar bundle and recover its embedded payload. Neither key, nor a key hash, is committed. The original experiment keys are unavailable in the saved artifacts; consequently, the committed bundles cannot be decrypted by a recipient who does not separately possess those exact keys. To reproduce the experiment, obtain the two keys securely from the original operator or generate new independent random keys and rerun, which produces a new bundle. Keep keys in a secrets manager or a local access-restricted store outside Git; inject them into the process environment without placing literal values in source files, command history, reports, or logs. Never publish keys alongside the bundles.

Run `python3 authenticated_tpe_nist_v2/scripts/prepare_four_pixel_inputs.py`, then install the pinned requirements in `authenticated_tpe_nist_v2/requirements-exact-order.txt`. Set `FOURPX_TPE_KEY_HEX` and `FOURPX_AUTH_KEY_HEX` through a trusted local secret manager, and run `python3 authenticated_tpe_nist_v2/scripts/run_four_pixel_auth_demo.py`. The runner uses 64 hex characters per key, writes to `output/four_pixel_authentication_demo_v2/`, and performs saved-file recovery in a fresh process. Save the exact keys securely if you need to decrypt that run later.

## NIST schedule-stream evidence

`upsilon_p_finalAnalysisReport.txt` and `substitution_r_finalAnalysisReport.txt` are the two schedule-stream diagnostics available with this work. Their original JSON manifests contain hashes for key, ImageID and generated bytes, not the secret values. The input ASCII bitstreams, the generation script, complete seed/parameter settings, and a complete STS invocation/configuration record are not included in the committed evidence. The local workspace had 100 sequences of 1,000,000 bits for each report, but exact regeneration is not supported by these manifests alone. Report-row failure counts are reproduced in `schedule_stream_report_summary.json`. These diagnostics are not the predeclared full NIST protocol and are not a v2 authentication-security result.
